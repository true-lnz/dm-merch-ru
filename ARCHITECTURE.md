# Архитектура проекта

## Общая схема

Проект построен на `Next.js 16` с `App Router` и объединяет две подсистемы в одном приложении:

- `frontend` — публичная витрина сайта;
- `Payload CMS` — административная панель, REST API и GraphQL API.

Payload встроен в тот же Next.js runtime, а не вынесен в отдельный сервис.

## Структура каталогов

- `src/app/(frontend)` — публичные маршруты сайта, layout и глобальные стили витрины.
- `src/app/(payload)` — встроенные маршруты Payload CMS: admin UI, REST API, GraphQL и служебные layout-файлы.
- `src/views` — page-level композиции для витрины.
- `src/widgets` — крупные переиспользуемые блоки интерфейса.
- `src/features` — пользовательские сценарии по мере появления интерактива.
- `src/entities` — бизнес-сущности фронтенда, их модели и UI.
- `src/shared` — общие UI-примитивы, конфиг и утилиты.
- `src/collections` — описания коллекций Payload CMS.
- `src/payload` — кастомизация административной части Payload, например графика и branding.
- `src/payload.config.ts` — корневой конфиг Payload CMS.
- `src/payload-types.ts` — автогенерируемые типы Payload. Файл не редактируется вручную.

## Роутинг

Роутинг задается стандартными файлами `App Router`: `page.tsx`, `layout.tsx`, `route.ts`.

Маршруты разделены через route groups:

- `src/app/(frontend)` обслуживает публичные страницы;
- `src/app/(payload)` обслуживает административную часть Payload и CMS API.

Для Payload используются отдельные route handlers:

- `src/app/(payload)/api/[...slug]/route.ts` — REST endpoints Payload;
- `src/app/(payload)/api/graphql/route.ts` — GraphQL endpoint;
- `src/app/(payload)/api/graphql-playground/route.ts` — playground для GraphQL;
- `src/app/(payload)/admin/[[...segments]]/page.tsx` — admin UI.

## Интеграция Payload CMS

Payload подключен на уровне Next.js-конфига через `withPayload(...)` в `next.config.ts`.

Текущая CMS-конфигурация:

- база данных — `SQLite` через `@payloadcms/db-sqlite`;
- rich text editor — `Lexical`;
- локализация — `ru` и `en`, fallback язык `ru`;
- текущие коллекции — `users` и `media`;

Переменные окружения для CMS:

- `PAYLOAD_SECRET`;
- `DATABASE_URL`.

На текущем этапе хранилищем выступает локальный файл `dm-merch.db`.

## FSD и границы зависимостей

Для публичной витрины сохраняется FSD-структура и правило направленных зависимостей:

`app -> views -> widgets -> features -> entities -> shared`

Обратные импорты между этими слоями запрещены.

Важно:

- это правило относится прежде всего к `frontend`-части проекта;
- `src/app/(payload)` и `src/collections` относятся к CMS-подсистеме и не обязаны повторять FSD-цепочку в том же виде;
- внешние слои должны использовать публичный API слайсов и не импортировать внутренние файлы admin/API части Payload.

## Публичный API слайсов

Для frontend-слайсов наружу должен экспортироваться только публичный API, обычно через `index.ts`. Deep import во внутренние файлы слайсов не допускается.

Это правило не распространяется на автогенерируемые файлы Payload и внутренние технические route handlers CMS.

## Источники данных на текущий момент

Инфраструктура Payload CMS уже подключена, но прикладной контент витрины еще не переведен на CMS полностью.

Текущее состояние:

- Payload используется как встроенная CMS-подсистема с базовыми коллекциями и admin/API инфраструктурой;
- часть витринных страниц продолжает работать на локальных данных и моках;
- например, блог сейчас рендерится из `src/entities/blog-post/model/mock.ts`, а не из коллекции Payload.

Документацию и код нужно читать с учетом этого разделения: CMS уже встроена в архитектуру, но не является единственным источником контента для frontend.

## Generated files и ограничения на правки

Некоторые файлы в `src/app/(payload)` создаются Payload автоматически. Их следует считать generated-слоем и не редактировать вручную без явной необходимости.

К generated-файлам относятся, например:

- `src/app/(payload)/api/[...slug]/route.ts`;
- `src/app/(payload)/admin/[[...segments]]/page.tsx`;
- `src/payload-types.ts`;
- `src/app/(payload)/admin/importMap.js`.

Ручные изменения в этих файлах могут быть перезаписаны инструментами Payload.

## Кодировки

В проекте есть файлы с кириллицей, поэтому все ручные правки таких файлов нужно сохранять в `UTF-8`.

Дополнительно:

- нельзя делать широкие repo-wide переписывания кодировок без отдельной задачи;
- после правок русскоязычного текста нужно проверять файл на mojibake;
- существующие проблемы кодировки в других файлах репозитория не меняют архитектурную схему, но их нужно учитывать при дальнейших изменениях.
